# 任务卡总索引 · Warband（ai_godot_projects）

> **这是什么**：把 `docs/PLAN.md` §E 的长期规划拆成**一条条可派工、可验收**的任务卡。
> **一张卡 = 一件事**，做完一张勾一张。
>
> **与 `PLAN.md` 的关系**：`PLAN.md` 是唯一的「现状」与「长期规划」来源；本目录只是**派工单**。
> 两者冲突时**以 `PLAN.md` 为准**，并回头修卡片。任务号进了提交信息之后就不要改（改成新号另开一张）。

## 一、怎么用

1. **只从「依赖」为空、且前置都已 ✅ 的卡开始。** 阶段一内部的顺序是**有依赖的**，不能跳。
2. 开工前先读卡的「待决问题」—— 那里列的每一条不答完，做出来大概率要返工。
3. 做完按下面「通用验收标准」逐条自查，再改卡的状态并提交。
4. 卡里写的「产出」是**预期**，实际改了别的文件不算错，但要顺手把卡的「产出」改准（`PLAN.md` §25.3：改动落地时就地更新）。

## 二、状态图例

| 图例 | 含义 |
|---|---|
| ⏸ 未开工 | 还没开始 |

| ⏭ 已跳过 | 决定不做（**必须写理由**，不许静默消失） |

## 三、设计成熟度（这一列很重要）

| 标记 | 含义 | 你该怎么做 |
|---|---|---|
| ✅ 已设计 | 需求、做法、验收标准都定过（阶段一全部 + 各阶段收口卡） | 可以直接开工 |
| 📝 待设计 | **只定了目标，做法没定**（阶段二~五的绝大多数） | 验收标准是**初稿**；第一条验收标准就是「**把设计稿写进本卡并复核**」 |

> 给待设计的卡「硬凑」精确验收标准是假的精确 —— 所以那些卡的第一条验收标准就是**先设计**。
> 这不是偷懒，是把「待设计」变成一条可执行的约定，否则待设计的任务会变成「边写边改需求」。

## 四、通用验收标准（每一个任务都适用，先过这 7 条再看卡里专属的）

| # | 条件 | 怎么查 |
|---|---|---|
| **L1** | **门禁全绿** | |`powershell -File tools\run_checks.ps1` → 末尾 `== 全部通过 ==`，且**项数只增不减**（2026-10-15 实测 **31**；已入库口径 30 —— 差的那 1 项是另一会话尚未入库的新检查） |
| **L2** | **新能力有守护** | 本任务新增的行为必须有**断言或门禁步骤**；「我手动试过」不算验收 |
| **L3** | **生成指纹不变**（除非本卡就是重基线任务） | 与 `tools/gen_fingerprint.json` **逐字节**比较。变了 ⇒ 说明碰了地图生成的 RNG 抽取顺序，**停下来查**，不许顺手重基线 |
| **L4** | **i18n 棘轮只许变小** | `ui_total` 不许涨（当前 **0**）、`project_total` 不许涨（当前 **631**） |
| **L5** | **性能不明显劣化** | 有可比的实测数字（对齐最近一次实时帧率实测的**同机位**）；没有数字就说「未测」，不要说「没影响」 |
| **L6** | **文档就地更新** | 本卡状态改 ✅（写完成日期 + 提交号）；`docs/PLAN.md` §D 记一行 |
| **L7** | **提交并推送** | 精确 `git add <路径>`（规则 G5：不吞在途文件）；提交信息说清「改了什么、为什么」；确认钩子输出 `pushed` |

### 三条纪律（比上面 7 条更容易破，单独写出来）

1. **不许把未验证的东西写成已验证。** 发现了但没修 ⇒ 写成**欠账**，不要写成已完成。
2. **不许悄悄放宽断言。** 放宽容差 / 删断言 / 改判据，必须在卡里写明**原因与影响**，否则就是掩盖回归。
3. **测量任务只测量，不下断言。** （`big_map_probe` / 帧率实测都属此类）测出来的数字要回填，但不要顺手加会变红的门禁。

## 五、编号与文件

- 任务号：`T<阶段号>-<两位序号>`。文件名 = `任务号-标题摘要.md`，标题就是卡里的 H1。
- **阶段内可以增删与重排**（重编号即可）—— 因为**没有任何代码引用任务号**（这与 `PLAN.md` §一–§十七 节号冻结的原因不同）。
- 一旦某张卡的号出现在提交信息里，就不要再改它；需要拆分时**另开新号**。
- 编号留出的空档（如 T5-10 之后）是给阶段五后续加项的，不必凑满。
